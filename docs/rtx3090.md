# bwarp on the RTX 3090

First measurements on an RTX 3090 (sm_86), with the tuning build of this branch: what the tunable
parameters gain there, and where the 3090 loses time against the RTX 5070 Ti that bwarp was developed on.
`tools/tune.sh` reproduces the tuning and benchmark tables.

## Machines

| | RTX 3090 box | Reference |
|---|---|---|
| GPU | RTX 3090, 24 GB, sm_86, 82 SMs, 6 MB L2 | RTX 5070 Ti, 16 GB, sm_120, 48 MB L2 |
| Driver | 616.92 | 610.88 |
| OS | Windows, bwarp running in WSL2 (Ubuntu 24.04), CUDA 13.3 | Windows 11 Pro, native, CUDA 13.5 |
| Build | `tools/tune.sh`: `linux-cuda` preset with `-DBWARP_TUNING=ON` | `build.bat` |

The 3090 box is also someone's desktop. Its GPU was idle during the runs, as far as `tools/tune.sh`
could tell.

## Tuning (2026-11-20)

`tools/tune.sh` at 0110212: coordinate descent over the `BWARP_TUNE_*` parameters on enwik9, each candidate
timed with `bench --context --pinned`, best of 5. A value was kept only if it beat the current one by more
than 0.5%, also when measured again back to back. The run took 30 minutes.

Tuned parameters: `MERGE_G=256 MERGE_TILE=128 MERGE_OVERFLOW_CAPACITY=1280 MERGE_OVERFLOW_THREADS=640`.
The others kept their defaults.

BWT construction, `bench --context --pinned`, best of 5 runs, in ms:

| File | Parameters | Upload | Ranking | Class sorts | Merge | Download | Total |
|---|---|---|---|---|---|---|---|
| enwik8 | default | 4.0 | 29.5 | 12.2 | 53.1 | 4.5 | 103.5 |
| enwik8 | tuned | 4.0 | 29.8 | 12.2 | 51.5 | 4.3 | 102.2 |
| enwik9 | default | 39.9 | 405.4 | 123.5 | 661.0 | 38.6 | 1268.8 |
| enwik9 | tuned | 39.8 | 402.4 | 124.4 | 613.0 | 39.1 | 1219.4 |
| enwik9 | 5070 Ti, default | 37.6 | 383.8 | 117.4 | 454.2 | 35.5 | 1028.8 |

- **The tuned merge parameters save 3.9% of the 3090's BWT construction on enwik9** (merge 661 → 613 ms).
- Ranking and the class sorts barely differ between the two GPUs (+5%), so the partitioning, which was
  sized for the 5070 Ti's 48 MB L2, isn't what holds the 3090 back. The merge is: +46% at the defaults.
- **The same parameters on the 5070 Ti:** no change in speed (1025.6–1030.9 ms against 1025.9–1029.4 ms,
  three runs each, interleaved), but 10.16 instead of 10.02 bytes of GPU memory per input byte. They are
  worth choosing per GPU rather than as new defaults.

## Whole process (LTCB settings)

`compress --segment 16 --slice 16` and `decompress`, wall clock of the whole process, best of 3 runs, round
trips checked byte for byte, as `tools/ltcb.ps1` measures:

| File | Parameters | Compressed | Compress s | ns/byte | Decompress s | ns/byte |
|---|---|---|---|---|---|---|
| enwik8 | default | 23,511,124 | 0.689 | 6.89 | 0.578 | 5.78 |
| enwik8 | tuned | 23,511,124 | 0.616 | 6.16 | 0.629 | 6.29 |
| enwik9 | default | 181,939,260 | 3.614 | 3.61 | 3.145 | 3.15 |
| enwik9 | tuned | 181,939,260 | 3.790 | 3.79 | 3.058 | 3.06 |

These are 2.2× (compression) and 3.4× (decompression) the 5070 Ti's 1.60 and 0.93 ns/byte on enwik9, although
its BWT construction is only 1.24× slower. They vary by about ±0.2 s from run to run, more than the tuning
saves, so they can't show the tuning's gain (the tuned enwik9 compression came out slower).

## Where the time goes (enwik9)

`compress --verbose --segment 16 --slice 16` and `decompress --verbose`, one run each, in ms:

| Compression | 3090 (WSL2) | 5070 Ti | Difference |
|---|---|---|---|
| Setup | 1922 | 213 | +1709 |
| Waiting to read | 597 | 54 | +543 |
| BWT | 1200 | 958 | +242 |
| Handover | 84 | 14 | +70 |
| Encoding (as printed, see below) | 633 | 78 | +555 |
| Total | 4384 | 1520 | +2864 |

| Decompression | 3090 (WSL2) | 5070 Ti | Difference |
|---|---|---|---|
| Setup | 1670 | 230 | +1440 |
| GPU | 456 | 285 | +171 |
| Waiting to write | 719 | 612 | +107 |
| Total | 2845 | 1127 | +1718 |

`ratio --gpu --verbose` (default `--segment 15 --slice 15`), the encoder's phases in the fused compressor,
in ms:

| Encoder phase | 3090 (WSL2) | 5070 Ti |
|---|---|---|
| Setup | 259 | 12 |
| Choosing tables | 34 | 30 |
| Coding tables | 16 | 13 |
| Streams | 82 | 18 |
| Placing | 260 | 12 |

Findings:

1. **Setup costs 1.4–1.7 s more on the 3090 box**, in both directions. Setup allocates the 1 GiB page-locked
   input buffer, initialises CUDA and reserves the GPU memory pool; decompression's setup allocates page-locked
   buffers of similar size. Suspected cause: page-locked host memory is slow to allocate under WSL2. Not
   verified yet; a native Windows run on the same machine would tell.
2. **Reading enwik9 took over 2.5 s**, since 0.6 s of it was still left after setup. Probably enwik9 wasn't
   (all) in WSL's file cache, or WSL's virtual disk is slow.
3. **The encoder's setup and placing contain the same ~248 ms, counted twice.** `reserveOutput()` allocates the
   page-locked output buffer once the compressed size is known; its time is added to `setupSeconds`, and it
   also runs inside the placing interval (`prepare()` in `encodeOnDevice()`, `src/cuda/gpubwarp.cu`). On the
   5070 Ti it takes about 10 ms, so the double count went unnoticed. The "encoding 633 ms" that
   `compress --verbose` prints is therefore about 390 ms of real time, ~250 ms of it that one allocation,
   which is again page-locked memory under WSL2.
4. **The stream encoder (`encodeSlices`) is 4.5× slower on the 3090**, the only real GPU gap in the encoder;
   choosing and coding the tables take about as long as on the 5070 Ti. Hypothesis, not verified: the
   frequency tables of the slices in flight don't fit the 3090's 6 MB L2, but do fit the 5070 Ti's 48 MB.

So of the 2.9 s the 3090 box loses on compressing enwik9, about 2.3 s are host overhead (setup, reading,
page-locked allocations), ~0.25 s the BWT construction and ~0.06 s the stream encoder.

## Next steps

1. Count `reserveOutput()` once, and allocate the output buffer during setup, where it overlaps reading.
2. Run a native Windows `bwarp.exe` (sm_86, tuning build) on the same machine, to separate WSL2's overhead
   from the GPU's.
3. Find out why `encodeSlices` is 4.5× slower on sm_86 (profiler, or fewer slices in flight).
4. Choose the merge parameters per GPU, e.g. by L2 size, so the 3090 gets its tuned values and the 5070 Ti
   keeps its lower memory use.

## Reproducing

On the 3090 box, with enwik8 and enwik9 in the repository root:

```
tools/tune.sh                                    # tuning, then the benchmark tables (report.txt)
unset CUDA_VISIBLE_DEVICES
build-tune/bin/Release/bwarp compress enwik9 /tmp/e9.bwarp --force --verbose --segment 16 --slice 16
build-tune/bin/Release/bwarp decompress /tmp/e9.bwarp /tmp/e9.out --force --verbose
build-tune/bin/Release/bwarp ratio enwik9 --gpu --verbose
```
